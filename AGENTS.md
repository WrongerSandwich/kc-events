# KC This Week

A weekly researched, ad-free list of what's worth doing in Kansas City. The idea, decisions, and first milestone are in `PROPOSAL.md`; read it before planning any work.

## Agent skills

### Issue tracker

Issues live in this repo's GitHub Issues, driven with the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

The five canonical triage roles use their default names (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one `CONTEXT.md` and `docs/adr/` at the repo root, created lazily as terms and decisions get settled. See `docs/agents/domain.md`.

## Concurrent sessions: one worktree per ticket

More than one agent session works this repository at a time (the lanes on #102), so every session works in its own git worktree and never in the main checkout, which stays on `main` and clean. In Claude Code, call `EnterWorktree` as the first step of a ticket, named after it (`71-cap-skipped-leads`): it makes `.claude/worktrees/<name>` on a fresh branch from `origin/main` and moves the session there. Elsewhere, `git worktree add ../kc-events-<ticket> -b <ticket>-<slug> origin/main`. In the worktree, `pnpm install --frozen-lockfile` once (the store is shared, so it is quick); tests and typecheck need no secrets, and a hand run needs the gitignored `.env`, copied from the main checkout and never committed.

Landing from a worktree: a serial-lane ticket (`run.ts`, adapters) rebases on `origin/main` after review and pushes its branch straight to `main` (`git push origin HEAD:main`); a site ticket, or anything running beside another session on the same files, opens a pull request from the branch. Remove the worktree when the ticket closes (`ExitWorktree` with remove, or `git worktree remove`). The weekly cron runs in its own clone (`~/kc-this-week-run`), so no worktree can collide with it.

## Commands

- `pnpm test`: the job's vitest suite (the root config leaves `site/` out); `pnpm -r test` runs it and the site's. `pnpm vitest run <file>` for one file.
- `pnpm typecheck`: `tsc --noEmit`.
- `pnpm test:coverage` (either package, or `pnpm -r test:coverage`): the suite with a v8 coverage report in `coverage/`, no threshold.
- The public site is the `kc-events-site` package in `site/`: `pnpm --filter kc-events-site dev | build | size | test | test:e2e`. `pnpm -r test` and `pnpm -r typecheck` run both packages; the site's typecheck is `astro check` and then `svelte-check`, the only one that checks the TypeScript inside `.svelte` files. The site's suite is two vitest projects: `unit` (`pnpm test`) and `data` (`pnpm --filter kc-events-site test:data`, the `*.data.test.ts` files), the checks of what the build makes of the committed dataset, which need `SITE_TODAY=last-run pnpm build` first and gate the weekly run's commit rather than pull requests (#191). `.github/workflows/site-ci.yml` runs typecheck, build, size, tests (with coverage, uploaded as an artifact), `test:data` (shown, never failing the job), and e2e on pull requests and `main`; the size check budgets the explorer, the front page and the 404 (a page with no island, so no Svelte runtime) on the fixture build and holds the real `explore.html` under a 200 KB ceiling. The fonts are committed in `site/src/fonts/`, Geist cut to the weights the site sets and Josefin Sans to the wordmark's capitals (renamed, as its licence asks); `site/scripts/subset-fonts.sh` (Python fonttools) remakes them after a fontsource bump or a change to the site's name. A build refuses fewer than 50 published events unless `SITE_ALLOW_SMALL=1` (the fixture build and the tests set it). The site's build also reads `data/venues.yaml`, the hand-kept venue table behind the venue pages (ADR 0013, how a row is added); the job never reads it. Every page is prerendered; the one function beside them is `site/api/report.ts` at `/api/report` (#129), which files a reader's wrong-listing report from the form on an event page or the About page as the issue the "Wrong listing" issue form would make (logic in `site/src/server/report.ts`, tested with GitHub faked; `site/e2e/report.spec.ts` serves it to the browser through a route). It reads `GITHUB_REPORT_TOKEN` from the Vercel project's environment (production and preview), a fine-grained token for this repository alone with Issues read and write, at request time and never at build; a Vercel Firewall rate-limit rule on the path `/api/report` (5 requests per 600 seconds per address) keeps it from being flooded, and the function itself files nothing once its token's owner has opened 20 issues in the last hour (issues filed by hand as the owner count too), and comments on an open `needs-triage` issue that already carries the same event rather than opening another, up to 20 comments on it (#187). `scripts/report-form-setup.sh` walks through the token, the variable and the rule.
- `pnpm research [--horizon-weeks N] [--no-discovery | --discovery]`: one run; `--no-discovery` turns the discovery lane off for it, `--discovery` runs it whatever its cadence. The lane runs on `discovery.cadence` (#255): `monthly` in the config, so only in a calendar month's first run (the dataset's `discoveryLastRan` is the day it last ran), or `weekly`; it does not follow a lead on a host already suggested for promotion, and its report section says whether it ran and why not, and how many leads it skipped. `pnpm research --reverify-only [--days N]` is the midweek re-verification instead (#253, CONTEXT.md): no list read, no search, no own page, nothing created; the primary pages of the events whose span covers a day from today through today + N (10) are read once each and re-verification applies what they say, then curation judges what changed. Its report has `mode: "reverify-only"`, `windowDays`, and the heading "Midweek re-verification <date>"; every report counts the pages re-verification read itself (`reverification.pagesRead`). It stops before any write when it fetched pages and none came back. Reads `research.config.yaml`, `prompts/extraction-rules.md`, `data/registry.yaml`, and `data/events.json`; writes `data/events.json`, `data/runs/<run date>.md` plus `.json`, and, when the run archives expired records more than eight weeks gone, the `data/archive/<year>.json` files they go to (added to, never rewritten from scratch; one that does not load stops every write): each to a `.tmp` beside it, flushed, and renamed into place only once all are written, so none is ever left truncated; nothing at all is written when the new dataset does not pass `parseDataset`, save the run's report and the refused records in full, in the gitignored `data/runs/<run date>.failed.json`, and the error names each refused record (id, title, status, class, start, end) with the schema's message (#219). Secrets come from env or a gitignored `.env` (`OPENROUTER_API_KEY`, needed as soon as the registry has an active source; `TAVILY_API_KEY`, needed unless discovery is off). Spend has two layers: `spendCapUsd` in the config stops model calls within a run (`src/spend.ts` wraps the model port), and a monthly limit on the OpenRouter key itself, set by hand through `scripts/hand-run-setup.sh`, backstops a bug in the first. Each registry page is read twice with `models.extraction` (`extractionReads: 2` in the config, 1 to drop back to a single read, #224): both calls start together and the first read's sightings merge ahead of the second's, so the second confirms what the first verified or covers what it missed; a page is not extracted only when both calls fail, its counts come from one read so they do not double, it is read in full when either read was, and the source's report line says how many sightings "the second read added". A page whose text runs past the 70,000-character cap (`MAX_PAGE_CHARS`) is cut there, and the report names the page, for a registry page on its source's line (#226). Discovery leads, re-verification and own pages are read once. Each of those stages reads `concurrency` pages at once (4 in the config, 1 for one at a time, #252) through `inOrder` in `src/pool.ts`: the model calls go out in page order, each checked against the cap (so a run can end about `2 × concurrency` calls past it), and every result is taken up in page order, so what a run writes does not depend on which page came back first; the golden test runs at 1 and at 4, and the test config sets 1 so scripted replies keep their order. A model call is one attempt, abandoned after 2 minutes for a page or 3 for a curation batch; the report's JSON twin lists every call (model, provider, generation id, cost, or the error, and the stage that made it and how long it took) to reconcile a month against OpenRouter's activity page, and the Markdown's Spend section tallies them by stage (calls, failed, USD, minutes; #257). A search gets one retry on a rate limit or server error; a spent Tavily quota stops the run's searches with one report line.

- `pnpm grade [--run YYYY-MM-DD]`: fills counts three and four of `docs/milestone-one-grading.md` from a run report (latest by default) and `data/events.json`, keeping whatever is hand-written around the marked blocks. Refuses a report whose horizon or cap is not the milestone's (3 weeks, 5 USD), and a midweek re-verification's.
- `pnpm promote <host> [--write]` (#255): prints the events held for promotion on a host, its discovery state, and a registry stanza drafted from them (the most common venue as its name, the distinct primary pages, most held events first, the most common kind and listed neighborhood, empty `checkHints`); `--write` appends it to `data/registry.yaml` under `# --- Promoted from discovery` once the registry parses with it. A person writes the hints and commits. Refuses a host already a source's, an aggregator or a platform. The logic is `src/promote.ts`, the CLI `src/promote-cli.ts`.
- `pnpm compare-models [--models a,b] [--repeats 3] [--cap 6] [--concurrency 2] [--refetch] [--tag name]`: the extraction model comparison (#222), outside the weekly run. Saves every active source's pages once to the gitignored `.cache/model-compare/` (reused until `--refetch`, so a model added later reads the same pages), has each model read each page `--repeats` times through `extractPage` in `src/run.ts`, and writes `docs/model-comparison/<date>.md`: quote pass rate, stability across repeats, agreement with the stored records, the hard cases in `src/model-compare.ts`, cost, time and failures, and the two-read measure (#223): each model once and twice and the first with each other, the saved sightings sent through `mergeSightings` and `foldDuplicates` against the stored dataset (stored records verified, kept, made unverified, unsighted, retitled; new records and likely duplicates; cost and minutes one after the other or side by side). `--tag` writes `<date>-<tag>` instead, leaving an earlier report that day as it was. Stops at its own spend cap; writes nothing the run reads. Switching `models.extraction` is a separate decision.
- `scripts/weekly-run.sh`: the weekly run, on a home machine's cron (ADR 0010), Mondays at 6:17 a.m. Central; `scripts/weekly-run.sh --reverify-only` is the midweek re-verification on the same cron, Thursdays at 6:17 (#253), passing the flag (and any `--days N`) to `pnpm research` and committing as "Midweek re-verification <run date>", with the same build, checks, push, wait on Vercel and health comment, but of the healthchecks.io pings only a failure (a Thursday success would keep a missed Monday from ever alerting); it refuses a day `main` already has a midweek pass or a weekly run for (its report would take the weekly run's file), and the weekly run's refusal stays keyed on its own commit. It runs in a clone dedicated to the job: resets to `origin/main` (abandoning any stopped rebase or undelivered commit), refuses if `main` already has a run for today (the manual workflow makes the same check), runs `pnpm research` (pass `--no-discovery` through) under a 90-minute timeout without the lock's file descriptor, builds the site from the new data and runs `test:data` on it (a failure stops the commit; the Always there picks the data leaves off the front page go in the report's "Site checks" section, never failing it), and commits `data/events.json`, that run's report, and any archive file it added to as "Weekly research run <run date>", then pushes; a rebase conflict with a commit that landed meanwhile re-applies the run's files on top of `main`. After the push it waits up to 15 minutes on the commit's `Vercel` status (`scripts/deploy-checks.sh`): a failed or unfinished deploy, or a status it cannot read, is a failed run, reported as one with the data already pushed. Every run comments on the one open `weekly-run-health` issue (created when missing): a line on success, the redacted log tail on a failure, either with the past week's failed nights from the daily deploy's log. That issue is a record that notifies no one (the token is the owner's), so when the clone's `.env` has `HEALTHCHECKS_URL` the run also pings that healthchecks.io check: a start, a silent success, or a failure carrying the comment's link; the check's one-week period alerts on a run that never starts, and its integration posts to Slack (#64). A failed run exits 1 and logs under `~/.local/state/kc-this-week/` (kept 90 days). One that fails before the push, a busy lock included, commits nothing; only the wait on Vercel comes after it. A run in which no active registry source can be fetched counts as failed (`run` throws before any model call), so a dead network cannot count an outage against every event. Likewise a run in which model calls were made and none succeeded (`run` throws at the end), so a model that is wholly down cannot leave every page unread; a single failed model call only costs its page or batch, reported as a problem.
- `scripts/home-run-setup.sh`: the wizard that makes the dedicated clone, installs Chromium for the browser fetch, puts the two keys in its `.env`, and with them `GH_TOKEN`, a fine-grained token for this repository alone (Contents and Issues, read and write; Commit statuses, read-only, for the wait on Vercel), makes `scripts/git-credential-env.sh` the clone's only git credential helper so the push uses that token and never the user's `gh` sign-in (`weekly-run.sh` hands the same token to `gh` for the health issue), asks for the Vercel Deploy Hook's URL (`DEPLOY_HOOK_URL`, in the same `.env`), and installs the cron lines (the weekly run, the midweek re-verification, the daily deploy), refusing when `node --version`'s major is not `.nvmrc`'s.
- `scripts/daily-deploy.sh`: the site's daily rebuild, on the same cron at 12:05 a.m. Central: a POST to the project's Vercel Deploy Hook, so the pages are built as of the new day rather than Monday's all week (the 2026-10-21 audit, E1: stale headings swapped on hydration, past events on the script-free kind, region and venue pages). Reads `DEPLOY_HOOK_URL` from the clone's `.env`, never printed; one line per day in `~/.local/state/kc-this-week/deploy.log`; a missing hook or an answer that is not 2xx exits 1 with a line there and tells no one else at the time, since the next weekly commit deploys regardless; that run's health comment lists the failed nights. The ignored build step (`site/scripts/ignore-build.sh`) builds a production deployment whenever the live site's `/events.json` was generated on another Kansas City day, so the hook's build goes ahead even after a docs-only commit (Vercel's previous SHA is the last successful deployment's, and such a commit's diff touches nothing the site reads).
- `.github/workflows/weekly-research.yml`: the same run on GitHub Actions, by manual dispatch only (with a no-discovery switch): the fallback when the home run misses a week. Two sources refuse GitHub's addresses (#22), so a fallback run counts an outage against their events. It refuses to start for a date the branch already has a weekly run for, builds the site from the run's data and runs `test:data` on it before committing (a failure commits nothing), and commits as "Weekly research run <run date> (manual run)"; a failed run commits nothing and says so in the job summary.
- `scripts/weekly-workflow-setup.sh`: the wizard that sets the two keys as Actions secrets from `.env` and offers to start and watch a first run.
- `scripts/hand-run-setup.sh`: the wizard for the hand run's human steps: OpenRouter and Tavily keys into the gitignored `.env`, and the monthly limit on the OpenRouter key.

The editorial surfaces are plain Markdown under `prompts/`: `extraction-rules.md` goes to the extraction model with every page, `curation-prompt.md` goes to the curation model with every batch of events it judges, and `event-page-rules.md` goes with every own page read (below). A wrong date or venue in the dataset is a bug in the first document; a don't-miss flag that reads as arbitrary is a bug in the second; a wrong time or price quoted from an own page, in the third.

The run function in `src/run.ts` is the one seam: it takes config, dataset, registry, and five ports (model, search, fetcher, browser fetcher, clock) and does no I/O. Test behavior there with the fakes in `test/fakes/`. `test/golden.test.ts` pins three weekly runs' datasets and reports as files in `test/__snapshots__/golden/`: a change to what `run` writes shows there as a diff, accepted with `pnpm vitest run test/golden.test.ts -u` once read. The site's tests build as of the last run's day (`SITE_TODAY=last-run`); only the test named "committed dataset is not stale" reads the real clock. The adapters are tested against a stubbed network (`routes()` in `test/fakes/network.ts`) and the recorded pages and robots.txt set in `test/fixtures/`; `test/fetcher.test.ts` holds the canned fetcher to the real one's answers, so change both together. The research command's I/O is `research()` in `src/research.ts`, tested in a temporary directory; `src/cli.ts` only loads `.env` and prints.

Choosing a source's fetch: the plain fetcher is the default. Give a registry source `fetch: browser` only when its listings are rendered by script, so the plain page has none (check with a plain fetch first). A calendar that shows its first page and fetches the rest by script may fetch them from an endpoint a plain GET reads, answering JSON with the listings' HTML in a string: list that endpoint's pages as the source's `urls` instead, since `readPage` reads a JSON object's HTML strings as the page, and the calendar's own URL as its `listedAt` (the Arts Council of Johnson County, #226). The pages are then one listing at that URL, which every sighting from them cites and which is never fetched: an event moving from page to page stays on one page, the pages' yields add up, and a page that does not come back, is not read in full, is cut at the cap, or reads as listing nothing holds all of the listing's events, the last two with a line on the source's report. When the last of the URLs lists a latest start inside the horizon, the source's report says to add the next page (#229). The browser fetcher (`src/adapters/browser-fetcher.ts`) walks the URL's redirects through the plain fetcher (robots.txt at every hop), loads where they end in headless Chromium with the same user agent, and returns the rendered HTML. A browser page gets one attempt within 30 s of its own (the plain fetcher's is 15 s), counted from the end of its origin's pause, so a crawl delay never eats into it. It reads the page once the network goes quiet; a page that never does (ads, live scores) or that fills its list after going quiet needs `waitFor`, a CSS selector for one rendered listing. A re-verification of an event from that source goes through the browser too, waiting for `waitFor`; discovery is always plain. An event's own page (the time read and the picks read, below) also goes through the browser, but never waits for the list's `waitFor`, which it does not render: it waits for `eventPageWaitFor` when the source sets one (Screenland's showtime button), else for the network to go quiet; give one only once an own page is seen failing (#153). Each fetch gets its own context (no downloads, no service workers, popups closed, frame navigations and requests to private hosts aborted). A redirect hop after a request's first URL can only be checked once it has gone out: a refused hop of the page's own navigation fails the fetch, and one of anything the page loads is a `WARNING` line in the log. Chromium runs in its sandbox, which needs unprivileged user namespaces: where the host has none it runs without, and the log says so in a `WARNING` line. The home run installs Chromium (`playwright install --only-shell chromium`, in `scripts/weekly-run.sh` and the setup wizard); the fallback workflow sets `BROWSER_CHANNEL=chrome` to use the runner's Chrome.

Reading own pages: after re-verification and before curation, every active event with an own page whose span covers a day from today through the horizon (it starts in that range, or started before today and has not ended, #151) has that page fetched the source's way and read by one model call (`src/own-page.ts`, `prompts/event-page-rules.md`, #254), nearest start first, at most `ownPageReadsPerRun` (150 in the config; 0 turns the pass off, as the test config does) a run, the rest read at a later run. The read asks for the time, the price and the age limit (each with its quote, `evidence.time`, `evidence.price`, `evidence.ages`) and a fuller description, which curation then judges from (an event already judged is judged again when the read fills out its description, `markChanged`): a time on the list's date, quoted from the own page, joins a start the list gave none. The list stays the primary page. Another date, or any failure, leaves the event as the list read it, and the report's "Own pages" section says so, on its "Upcoming events" line (read, filled, kept, left for next run, failures). `ownPageRead` records the read, and what it gave is kept while the list keeps the date and the own page, so a page is read again only when one of them changes (ADR 0009, amended #123, #133, #254). A host whose robots.txt refuses an own page is not fetched again that run: one line on the report names it and counts the events held back, with no call spent. A pick the ceiling left is read after curation instead, on the report's "Picks" line. For a limited run the read also asks for the weekdays it plays (`days`, quote in `evidence.days`, #143), only when the page states them or lists its performances; when the own page gives none and links a page of performances (a box office's "Get Tickets"), that page is fetched and read for the days alone, one more call, if it is on the venue's site or a ticketing platform. A platform whose pages render by script is fetched through the browser, waiting for its selector in the config's `platformWaitFor` (OvationTix); anywhere else, the source's way. The days are kept with the read. Extraction also fills `days` from a list's own date line when it names the weekdays ("Wednesdays, Oct. 7-28", #196): quoted as the event's date, from the primary page, which must state them (in the plural, as a span, or as weekends; a weekday beside a date is the date's), and refreshed with every reading of the list; an own page's days stand over the list's, and an own page giving none leaves the list's and does not follow its ticket page. A reading the model gave a schedule and no end whose date quote gives one month-day span ("SATURDAYS & SUNDAYS / Nov 28th – Dec 20th") is read as that span, a limited run with the days its quote states, and the source's report line says so (#218); a season named by its months alone ("Every Sunday, April thru October") stays recurring, and so does a quote that names such a season beside its span, as a row of a year's hours by season does ("April–November: Sat & Sun … Nov. 1 – Nov. 22: Sat & Sun", #221). The site shows a run with days as on now, in the week's running band, and in the calendar export (a weekly rule) on those weekdays only.

Both fetchers go through one fetch policy (`src/adapters/fetch-policy.ts`), checked at every redirect hop: http(s) only, no literal IPs, dotless, `.local`, `.internal` or `.localhost` hosts, or hosts resolving to a private address; a body budget of 5 MB; a content-type allow-list; the declared charset; and a pause per origin (robots.txt `Crawl-delay`, capped at 10 s, else 1 s). A refusal throws `FetchRefused`, which the run counts as an outage.
