KC This Week · how the job works

How a research run works, and how it gets reviewed

Every Monday a job on the home machine reads about fifty venue calendars, checks each event against the page it came from, judges which ones are picks, and commits the result. Then a second pass, and you, look over what it did. This page walks through both in pictures.

1 · The week

Three scheduled things, and you

Two cron lines on the home machine do the research. A third rebuilds the site each night so its dates stay right. A Claude routine audits Monday's run and emails you.

2 · Around the run

What scripts/weekly-run.sh does before and after

The script runs in its own clone, ~/kc-this-week-run, so nothing you have open can collide with it. Everything above the red line can fail without touching main.

3 · Inside the run

One function, fourteen steps

All the logic is run() in src/run.ts. It does no I/O of its own: it is handed files that were already read and five ports to the outside world, and it hands back a new dataset and a report. That is why the tests can run a whole week with fakes.

4 · Page to sighting

Cite-or-drop: nothing publishes without a quote

The model is never trusted on its word. For every event it reports it must quote the page for the date and for the venue, and code checks that both quotes are really there.

5 · Matching

Is this sighting an event we already have?

An event is recorded once, however many pages list it and however its date moves. Each sighting climbs down this ladder; the first rule that matches a stored event wins.

Then: does that page get a say?

A match only says the sighting is about a known event. What it may do to that event depends on where it was read.

6 · Life of an event

Three statuses, and the ways between them

The site publishes active events and nothing else. Everything else stays in data/events.json so the job remembers what it has already seen and decided.

7 · Strike or outage

What re-verification concludes when it re-reads a page

The principle is ADR 0008: an outage holds an event; only a reading strikes it. A page that could not be read says nothing about whether the show is still on. Most of this ladder exists to tell "the venue dropped it" apart from every other reason an event might not be in a reading.

8 · Picks

How an event becomes a pick

Curation asks one question of each event: picture a mixed group of friends planning something to do; would someone bring this up, and why? The answer is a verdict with a named reason, not a score.

9 · Guards

What stands between a bad run and the site

Five layers, left to right. A run has to get through all of them before a reader sees its data.

10 · Review loop

How a run gets reviewed, and how a finding becomes a fix

Nothing in the run reviews itself beyond the guards above. The review is a loop around it with three readers: the Monday audit routine, you, and the site's readers.
