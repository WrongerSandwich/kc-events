# The weekly run is scheduled on a home machine; GitHub Actions is the manual fallback

Two registry sources (Crossroads Arts District, KC Parks and Recreation) return 403 to GitHub-hosted runners' addresses and 200 to a home connection with the same user agent, and under ADR 0008 three weeks of that hid every event they carry. The run is incremental and commits to this repo (ADR 0006), so where it runs is a choice. We moved the schedule to a cron on Evan's always-on home machine (`scripts/weekly-run.sh`, set up by `scripts/home-run-setup.sh`) and kept the GitHub workflow as a manual-dispatch fallback for a week the home run misses. The same move makes a browser-backed fetch (#56) a one-time local install, and gives the sources that refuse any datacenter address (#57) a residential one, whatever is decided there.

This amends ADR 0004, which placed the job on GitHub Actions so that nothing public gates on personal infrastructure. The job, its dataset, and a complete way to run it (the workflow) all stay in the public repo, and nothing personal is exposed; only the weekly cadence now depends on one machine, and a missed week is a button on the Actions page, not an outage. Of the alternatives, routing the two blocked fetches through a home tunnel needs both machines plus a tunnel for the least gain; excluding the two sources loses KC Parks entirely and the Crossroads galleries and First Fridays; a self-hosted Actions runner on a public repo is against GitHub's own advice.

Consequences: ADR 0006's note that the weekly commit keeps GitHub from disabling the schedule no longer applies, since only scheduled workflows are disabled and this one has no schedule. Home-run commits come under Evan's git identity rather than the Actions bot, and a failed home run surfaces as a `needs-triage` issue opened by the script, where a failed workflow run surfaced as a red job and an email.
