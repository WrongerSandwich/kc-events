# An outage holds an event; only a reading strikes it

Two-strike expiry used to count any failed re-verification, so a page that could not be loaded (a connection reset, a 403 from a site blocking the job's runner, a 5xx) struck an event exactly as a page that no longer listed it did. One blocked runner address was enough to expire every event from a healthy venue in two weeks. Now only a reading strikes: the page loaded and no longer lists the event, is gone (404 or 410), or its `robots.txt` now disallows the job. A page that cannot be loaded is an outage, which neither adds a strike nor clears one. The event is held as it was through up to three consecutive outages, then becomes `unverified` (hidden, not expired) and keeps being re-checked each run until its page lists it again or it is past.

This sets what "a recent run" means in cite-or-drop (ADR 0002): a published reading is at most three outages old, and its last-verified date is shown. We chose hold-then-unverify over striking on outage, which loses good events to bad networks, and over holding indefinitely, which lets a stale reading publish for the whole of a limited run.

**Amended (#19):** the outage limit is no longer the only way a verified event becomes `unverified`. A page that still lists an active event but whose re-reading cites no date or venue now hides it at once, keeping its old reading and curation and clearing its strikes, since publishing a reading the rules no longer support breaks cite-or-drop. Both kinds of hidden event are re-checked against their primary page each run until they are past, including one a lane sighted when the lanes did not try its primary page this run. A verified reading brings either kind back under the same id. Only a re-reading of the event's own primary page hides it this way (#16): another page that matches it fuzzily, such as one naming no venue, cannot speak for its own page's reading.

**Amended (#39):** a reading that leaves out an event starting after the run's research window (`horizonWeeks`) is not a strike. Extraction is asked only for events within that window, so the page's silence says nothing, and the event is left as it was: no strike, no refresh, its strike and outage counts unchanged. A page that is gone or that robots.txt disallows is still a strike for every event on it, whatever its date. The run report counts the events left unstruck this way.

**Amended (#75):** which pages may say anything about a known event is now a question of standing. Through 2026-10-10 any verified sighting that matched an event could cancel it or refresh its whole reading, primary page included, and any sighting from the event's own page could cancel it; a page the search ranked, or a link off an aggregator page, had the same say as the venue's calendar. Now a page speaks for an event only when it is the registry lane's (a source a person admitted) or on the event's own site, its primary page's registrable domain. Only such a page can cancel the event or refresh it. A sighting from anywhere else confirms the event at most: the event is still listed somewhere, so its strikes and outages clear and nothing else moves. A cancellation from anywhere else is not a sighting at all: the event is left as it was, which sends it to re-verification against its own page, and the run report names the page and what it said ("Cancellations from elsewhere"). The uncitable-reading rule above keeps its narrower condition: only the event's own primary page hides it. A refresh also keeps the stored title when the new one is the same title cut short or with a series name in front, the forms identity (ADR 0007) already treats as one title, either way round, so the form seen first stays and a page that bills a show two ways does not flap the site between them. The site is the registrable domain, for want of a public suffix list, with one exception: a ticketing platform the config lists is no one's site, since any organizer can put a page on it, so two pages there never speak for each other. Two tenants of any other hosted platform still count as one site, the approximation's known cost. A confirming page is still a sighting, so an event a third-party page keeps listing is not re-verified against its own page while it does; that hole is #78's.
