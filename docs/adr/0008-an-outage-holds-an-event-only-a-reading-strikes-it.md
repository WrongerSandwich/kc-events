# An outage holds an event; only a reading strikes it

Two-strike expiry used to count any failed re-verification, so a page that could not be loaded (a connection reset, a 403 from a site blocking the job's runner, a 5xx) struck an event exactly as a page that no longer listed it did. One blocked runner address was enough to expire every event from a healthy venue in two weeks. Now only a reading strikes: the page loaded and no longer lists the event, is gone (404 or 410), or its `robots.txt` now disallows the job. A page that cannot be loaded is an outage, which neither adds a strike nor clears one. The event is held as it was through up to three consecutive outages, then becomes `unverified` (hidden, not expired) and keeps being re-checked each run until its page lists it again or it is past.

This sets what "a recent run" means in cite-or-drop (ADR 0002): a published reading is at most three outages old, and its last-verified date is shown. We chose hold-then-unverify over striking on outage, which loses good events to bad networks, and over holding indefinitely, which lets a stale reading publish for the whole of a limited run.

**Amended (#19):** the outage limit is no longer the only way a verified event becomes `unverified`. A page that still lists an active event but whose re-reading cites no date or venue now hides it at once, keeping its old reading and curation and clearing its strikes, since publishing a reading the rules no longer support breaks cite-or-drop. Both kinds of hidden event are re-checked against their primary page each run until they are past, including one a lane sighted when the lanes did not try its primary page this run. A verified reading brings either kind back under the same id. Only a re-reading of the event's own primary page hides it this way (#16): another page that matches it fuzzily, such as one naming no venue, cannot speak for its own page's reading.

**Amended (#39):** a reading that leaves out an event starting after the run's research window (`horizonWeeks`) is not a strike. Extraction is asked only for events within that window, so the page's silence says nothing, and the event is left as it was: no strike, no refresh, its strike and outage counts unchanged. A page that is gone or that robots.txt disallows is still a strike for every event on it, whatever its date. The run report counts the events left unstruck this way.

**Amended (#75):** which pages may say anything about a known event is now a question of standing. Through 2026-10-10 any verified sighting that matched an event could cancel it or refresh its whole reading, primary page included, and any sighting from the event's own page could cancel it; a page the search ranked, or a link off an aggregator page, had the same say as the venue's calendar. Now a page speaks for an event only when it is the registry lane's (a source a person admitted) or on the event's own site, its primary page's registrable domain. Only such a page can cancel the event or refresh it. A sighting from anywhere else confirms the event at most: the event is still listed somewhere, so its strikes and outages clear and nothing else moves. A cancellation from anywhere else is not a sighting at all: the event is left as it was, which sends it to re-verification against its own page, and the run report names the page and what it said ("Cancellations from elsewhere"). The uncitable-reading rule above keeps its narrower condition: only the event's own primary page hides it. A refresh also keeps the stored title when the new one is the same title cut short or with a series name in front, the forms identity (ADR 0007) already treats as one title, either way round, so the form seen first stays and a page that bills a show two ways does not flap the site between them. The site is the registrable domain, for want of a public suffix list, with one exception: a ticketing platform the config lists is no one's site, since any organizer can put a page on it, so two pages there never speak for each other. Two tenants of any other hosted platform still count as one site, the approximation's known cost. A confirming page is still a sighting, so an event a third-party page keeps listing is not re-verified against its own page while it does; that hole is #78's.

**Amended (#78):** several readings that said nothing about an event used to strike it; now a strike needs a reading that is about the event. A page a person excluded from the registry is not fetched for re-verification at all (through 2026-10-10 an excluded source was still hit weekly, by name, until its events expired): its events are held as through an outage, so they hide at the outage limit and come back when the source is active again, and the run report names the source and the count. A page that loaded and read as listing nothing, where three or more active events would be struck, is an outage for that run, not a strike each: a page that rendered empty, or a model that returned nothing, is not news about every event on it; the report names the page. An omission is not a strike when the event starts after the latest start the page listed this run, as it is not when the event starts after the horizon: the page's window moved ("the next 20 shows", a month view) rather than the venue dropped the event; the report counts these beside the horizon's. The horizon the model is told now names its last date, and the horizon rule gives two days of slack at its end, since a model told only "the next N weeks" stops a day or two short of the date the job counts to. A page with no standing toward an event (amended #75) now says nothing about it, not even that it is still listed: through 2026-10-10 such a page confirmed the event, clearing its strikes and keeping it from re-verification while a third-party page kept listing it; now the event is left as it was, strikes included, and re-verified against its own page, which alone decides. And when one page lists the show on two nights within the fuzzy window, the night nearest the stored start is the event's reading, whichever the page gives first; the first listed used to win, so a record could jump to an earlier night.

**Amended (#111):** a registry calendar whose redirects end on an index page (an aggregator's listing, a ticketing platform's search) is an outage for the events citing it, not a strike each. Through 2026-10-11 extraction skipped the page but re-verification counted it as read, so every event on a calendar the venue moved behind an index page took a strike, and two such weeks expired them all; a discovery lead that redirects to an index page was already an outage. The source's report line still names the index page, which is how a person learns the calendar moved.

**Amended (#124):** a re-reading of an active event's own primary page that fails only on a quote (the model's quote is not on the page, though it gave a date and a venue) no longer hides the event when nothing about the page says the reading has changed: the event's stored date and venue quotes are both still on the page this run read, and the new reading agrees with the stored one (the same calendar date, the same time when both give one, or the same schedule for a recurring event, and the same venue, case and spacing aside). The event stays `active` on its stored reading, evidence and curation, its strikes and outages clear, and its last-verified date moves to this run, since its stored quotes were checked against today's page. Through 2026-10-12 a stitched or embellished quote (a "Buy Tickets" left out of a multi-line span, an address added from elsewhere) hid such an event at once, and the site flickered from run to run on an unchanged page; the second hand run that day hid 22 events this way whose stored quotes were all still on their pages. Any other uncitable reading (a date that does not exist, no date or venue), a stored quote no longer on the page, or a reading that disagrees still hides the event as in #19, and an event already `unverified` comes back only on a verified reading. The run report lists the events kept this way, with the failed quote ("Kept on its stored citation"), so model variance stays visible.

**Amended (#220):** the agreement test above is narrowed to the day and the venue. It failed on the commonest misses: a recurring event's schedule is the model's own wording, which changes between readings, and a time taken from an own page or another reading (19:00 from a schema.org line) never matches a list's doors time (18:00). The 2026-10-23 afternoon run hid 17 verified events on a missed quote, First Friday among them. Now the event is kept on its stored reading when its stored date and venue quotes are both still on the page this run read and the reading gives the same calendar date (a recurring reading of a recurring event, whatever its schedule's words) and the same venue under the venue rules (aliases included). The time and the schedule's words no longer count. The day and the venue still do: the stored quotes on a page cannot by themselves say an event has not moved, since a calendar keeps a moved show's old date quote while another show plays that night, and a single-venue calendar names its venue on every listing. A reading whose quotes pass refreshes the event as before.
