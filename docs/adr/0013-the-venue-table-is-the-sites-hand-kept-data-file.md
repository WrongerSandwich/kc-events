# The venue table is the hand-kept venue data file

*Amended 2026-11-08 (#258): the table holds a venue's neighborhood too, and the job reads it for that; the title said "the site's own" before.*

A venue page (#137) needs what no page the job reads gives reliably: the venue's street address, its position, and its own site. That is hand-kept data, and it needed a home. The job already keeps one hand-kept list about venues, `venueAliases` in `research.config.yaml`, so a section beside it was the obvious candidate.

The table is `data/venues.yaml` instead, one row per venue, read by the site's build for the page and by the job for one field, the neighborhood (below). The research job never reads an address or a position, so putting them in its config would make an address fix an edit to the run's settings, reviewed as one, and would put a site-only list in the file every run parses. `venueAliases` stays in the config because the job uses it to match events; the table keys on the display name that list produces (the venue's alias key, or the name as pages give it when it has none) and adds nothing to matching. Kept beside `data/events.json` and `data/registry.yaml`, it is in the place a person looks for the job's hand-kept data, and like them it is committed.

**The neighborhood is a row's field (amended 2026-11-08, #258).** A venue's neighborhood began as a second hand-kept list, `venueNeighborhoods` in the config (#150), six rows the run applied each week while the table held forty-three with addresses and positions, so one venue's facts lived in two files and a venue the extractor kept misplacing (the 1900 Building, proposed as "Mission Woods" twice) had to be pinned in the run's settings. Now a row may carry `neighborhood`, one the config's regions list and never the catch-all, and the run reads the table at its start and places every event not expired at that venue there, read that run or not, as the config list did; the list is gone. The address and position stay the site's alone: the job parses every row (`src/venues.ts`, and the site's build parses through the same function) but reads only the name and the neighborhood. A table that does not parse stops the run before any write, as the registry does, and the report names every venue with active events and no row, most events first, so the table grows where it matters. The venue page's own neighborhood still comes from its events, which the row places, so the two agree.

The build holds the two lists together: a row keyed on an alias (it names the key to use), on a known venue spelled another way, or two rows for one page fail the build with the row named. A row whose venue no record in the dataset is at only warns (amended 2026-10-21): the job archives expired records eight weeks on, so a quiet venue's row would otherwise refuse the weekly data commit's build and the site would stop refreshing; its page lists nothing until an event appears there. A page's slug is derived from the name, never stored: a result row in the explorer links its venue's page with nothing added to the event data the explorer carries, so the slug cannot be overridden, and renaming a venue's display name moves its page.

**How a row is added.** Add the venue's display name exactly as the site shows it (if the venue should go by another name, or its rooms be merged into it, change `venueAliases` first), its address on one line as `<street>, <city>, <MO|KS> <ZIP>`, and optionally `lat` and `lng` (both or neither; look the place up, as on OpenStreetMap, never from memory) and `url`, the venue's own site. A district with no one street address (the Crossroads) gives a position instead of an address; a row needs one or the other. Check the row by opening its page's map link. Add `neighborhood` only when the pages keep placing the venue wrongly or nowhere (the report's "Venue neighborhoods" and "Unmappable neighborhoods" sections say which): one a region of the config lists, spelled as the list spells it, never the catch-all; the next run moves the venue's events there and its report counts them. A venue with no row still has a page, with its events and neighborhood alone, and the report's "Venues without a row" section lists it while it has events.
