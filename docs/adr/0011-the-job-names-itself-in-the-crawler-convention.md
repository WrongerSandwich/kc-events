# The job names itself in the crawler convention, and never as a browser

Some sources refuse a request because of its user agent alone. When #57 was checked from home on 2026-10-08, the Renaissance Festival refused any user agent containing "research". Other sites refuse anything that does not start with `Mozilla/5.0`; the 403 recorded for the KC Current came from a rule like that, on a domain that turned out not to be the club's. The user agent the job had used since the start, `kc-events-research/0.1 (+repo URL)`, matched both rules. We changed it to `Mozilla/5.0 (compatible; kc-this-week/0.1; +https://www.kcthisweek.com/about)`, and its robots.txt token to `kc-this-week`. This is the form search engines' crawlers use. The `compatible;` wrapper is a convention for clients that are not browsers, and the product token and the link name the job plainly. The about page's "For venues" section says what the job is and how to keep it off a site.

The line this draws, which ADR 0001's "what search engines do" posture depends on: the job always names itself and obeys robots.txt. It never sends a browser's own user agent, and never hides the headless browser from #56 to get past a bot check such as Cloudflare's JavaScript challenge. A site that still refuses the job after that has said no to automated clients. It stays excluded, with the mechanism recorded in the registry, until the site allows the job. Kansas City Museum and Funny Bone are both in that position.

The rename also takes "research" out of the name, which predates KC This Week. On 2026-10-08 the change was checked against every active source with a plain fetch under both user agents, and none changed its answer except to let the Renaissance Festival through. The new robots.txt token means a site's rules for `kc-events-research` no longer apply; none of the sources had any.
